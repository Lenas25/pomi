# Pomi — project notes for Claude Code

Open-source, local-first Android app (gym + healthy habits). Spec: `PLAN.md`. Design: `design/` (`HANDOFF.md`, `BRAND.md`, `ASSETS.md`, `tokens.json`).
Work by milestones (PLAN §18): tests green, one Conventional Commit per milestone, short summary.

## Language contract

- Code, identifiers, comments, commit messages, this file: **English**.
- User-facing strings live ONLY in `src/i18n` (`es` default, `en`). Route file names follow PLAN §5 (Spanish): `hoy`, `gym`, `habitos`, `progreso`, `ajustes`.
- No written content in code: exercises, habits and check-in texts come from `templates/` and i18n.
- Commits: Conventional Commits, no `Co-Authored-By` or AI attribution (user rule).

1. Decide/confirm the Android package, replace `CONTACT_EMAIL_PLACEHOLDER` and `REPO_URL`.

## Technical decisions

### Design / UI

- **Theme: light / dark / system only.** No "rosa/morado" accent theme exists (PLAN §13 / `templates/settings.json` `accent` are superseded). Setting value: `'system' | 'light' | 'dark'`, default `system`; held in `useThemeModeStore`, persisted in settings key `themeMode` (hydrated at startup by `useDatabaseReady`).
- **`design/tokens.json` is the single source of truth.** The only theme module is `src/ui/theme` (import it from there; `design/theme.ts` was removed). Components use ONLY theme tokens (no literal colors, sizes or font names). M0 added tokens `control` (button heights 48/56), `layout.maxContentWidth` (560), `stroke`, `opacity` (disabled/pressed) `motion.pressScale`, `color.transparent`, `layout.tabBarHeight` (scaled by the system font scale in the tab layout) and `icon.size`. `textStyle` throws in `__DEV__` when a font weight is not loaded.
- **i18n is reactive:** components call `useT()` (bound to `useLocaleStore`); the plain `t` is for non-React code. The language preference (`system | es | en`) is persisted in settings key `language` (`system` = key removed) and hydrated by `useDatabaseReady`.
- Interactive `Card` requires `accessibilityLabel` (discriminated props). `MascotPose` is derived from `mascotImages`. `noUncheckedIndexedAccess` is on.
- **Fonts:** heading = Fredoka (600, 700); body = Nunito Sans (400, 600, 700); numeric (timer/metric) = Nunito 900 with tabular digits. Loaded in `app/_layout.tsx` before hiding the splash.
- Icons: Phosphor, `IconContext` default weight `bold`, size 24, color from theme (`IconProvider`). Template `icon` emojis map to Phosphor icon names; emoji is allowed only in notification text (max one).
- Mascot is decorative (`accessible={false}` + `importantForAccessibility="no-hide-descendants"`); `MascotBubble` is a polite live region and warns in dev above 40 chars. Reduce-motion (`useReducedMotion`) disables scale/translate, keeps a 120 ms fade, and press feedback keeps the opacity dim.
- Android package is a placeholder `pe.nakea.pomi` (BRAND says the name/package is still to be decided). `minSdkVersion` 26 (Health Connect).
- **Charts: `react-native-svg`, no chart dependency** (PLAN §4 asked to justify victory-native vs svg). Reasons: svg is already installed (TimerRing), victory-native would add Skia + a second animation stack to a development build for two simple charts, and token-styled components (`LineChart`, `BarChart`, `src/ui`) stay fully themeable (light/dark, tokens only), testable in Jest and accessible as ONE `image` with a spoken summary (the drawing is hidden from TalkBack). Geometry is pure (`src/ui/chartMath.ts`: nice axis ticks, scales, paths); the chart measures its own width (works in 1 or 2 columns) and fades in (240 ms; 120 ms with reduce motion). Chart sizes are tokens (`chart.*`). Revisit only if a chart needs gestures (zoom/scrub).

### Templates and data

- Template schema extends PLAN §6.2 with `muscles`, `rules`, `onlyIf`, `glassMl`, `source` (implemented in `src/templates/schema.ts`).
- **Template `icon` = Phosphor component name** (PascalCase, e.g. `Barbell`, `Drop`); emoji is rejected by the importer. Schemas are strict: unknown keys are errors (`unknownKey`, with the full path) except keys starting with `_` (e.g. `_note`), which the importer strips from schema objects before validating; open maps (`onlyIf`, listed in `OPEN_MAP_FIELDS`) keep their keys verbatim.
- **Importer** `importTemplate(json)` / `importTemplateFromText(text)` returns `{ok, template}` or `{ok:false, errors[]}`; each error is `{code, path, params, line?}`. Show them with `describeImportError(error, t)` (messages live in `importErrors.*` i18n, es + en). Bundles (`kind: modules`) are split into module rows via `toModuleTemplates`; `kind: settings` is applied to settings/profile, never stored as a module.
- **Bundled defaults:** `loadDefaultTemplates()` validates `templates/*.json`; `templates` repository `seedDefaults()` seeds the modules once (flag `templatesSeeded`). The settings template is only an author example and is not seeded.
- **Exercise history key = step id** (global across routines); today's routine supplies the rep range.
- **reps parser:** `"8–10"` → `[8,10]`; single number (`"8 por lado"`) → `[8,8]`; seconds ranges (`"30–45 s"`) are time, not reps; compound text (`"12–15 + 10 pulsos…"`) uses the first range; bodyweight (no `incrementKg`) only gets +1 rep.
- **Gym days source of truth = settings** (from onboarding), not `program.schedules`.
- `bed` is derived: `wake − sleepTargetH`.

### Formulas

- **Water:** 33 ml/kg + 500 ml per gym hour (1 h per session by default), rounded **UP** to 250 ml glasses.
- **Steps v1:** goal fixed after the baseline week (baseline + 1000, rounded to 500, cap 10000). Weekly auto-adjust only through suggestions (v2), never silently.

### Companion features (PLAN §14b)

- **v1:** evening "¿Te moviste hoy?" notification with actions (gym / walk / no) writing `activity_logs` even with the app closed ("Hoy no" is never a miss); sleep-cycle calculator (`wake − n×90 − 15`, n = 4..6).
- **v2:** sleep debt (7 days, daily surplus capped at 60 min, min 4 days), social jetlag (midsleep difference, 14 days), water curve by hour (suggestions only), "Tu ritmo" profile (min 21 days, prudent wording), Sunday "Carta de Pomi", configurable sedentary nudge from Health Connect hourly steps in a background task (approximate, ~15 min; Android may delay it).
- **v3:** optional on-device LLM ("Pomi conversa"): deterministic engines compute every number, the LLM only verbalizes via tool calls, strict healthy-life scope, no medical advice, template fallback.
- Every number comes from a pure engine in `src/domain`; text generation never computes.

### Routine generator, BYO AI and on-device LLM (PLAN §14c-§14f)

- **v2 generator:** pure `generateProgram(input)` -> program in the existing template JSON, from a curated `templates/exercises.json` library (data, not code). Every rule cites an evidence id `E<n>` = section `<n>` of `docs/evidence/training.md`; `[DESIGN]` items there are documented defaults, never findings. PAR-Q+ screening (7 questions) comes first: any "yes" shows a professional-advice notice and requires acknowledgement (generation limited to the low-intensity beginner template), never medical advice. The result is a PROPOSAL (preview, edit, accept). Deload is reactive only. ACSM 2026 position stand supersedes 2009 (only its abstract was read).
- **v3 "Conectar mi IA":** BYO provider via an OpenAI-compatible adapter (incl. custom base URL for Ollama / LM Studio / vLLM) and an Anthropic adapter; key in `expo-secure-store` (NEW dependency, approval pending, do not install yet); explicit opt-in; the exact outgoing payload (aggregates only, no photos/notes by default) is shown before every send; engines compute numbers, AI only verbalizes via tool calls; routine changes go through generator validation + user acceptance.
- **v3+ on-device LLM:** `llama.rn` + Qwen3.5-2B Q4 (0.8B fallback, 4B for >= 8 GB), optional hashed download, ONLY after a real-device benchmark; no vector RAG (FTS5 for notes).
- `pomi-server` (self-hosted learning companion) is an idea outside the roadmap: it breaks local-first, so it would be a separate repo.

### Timers and notifications

- **Model** (`src/timers/timerModel.ts`, pure): a running timer stores `endsAt`; pause stores `remainingMs`; resume derives a new `endsAt`; `+30 s` grows `endsAt`/`remainingMs` and the total (a finished timer is not revived); skip = finished. Everything is re-derived from `Date.now()` (`syncTimer`), so backgrounding costs nothing.
- **One active timer** lives in the vanilla zustand store `createTimerStore(effects, now)` (`timerStore.ts`, singleton via `getTimerStore()`); a new `start` replaces the previous one. Effects are injected (`TimerEffects`), so the store is tested with fakes. Owners: `rest:<stepId>:<setIndex>`, `hold:<stepId>:<setIndex>`, `wait:<stepId>`, `timed:<stepId>`; `cancel(owner)` only affects that owner (✓ undone cancels ITS rest).
- **Background alarm = ONE local notification at `endsAt`** (expo-notifications `DATE` trigger, `channelId: 'timers'`), scheduled on start/resume/+30 s and cancelled on pause/skip/cancel/finish. A scheduling result that arrives after the timer changed is cancelled (`revision` check; the revision comes from a MODULE-level monotonic counter, so it is never reused, and `startedAt` identifies the run). `pause()` / `addTime()` on a timer that already ran out finish it through the normal `elapsed` path. The effect re-checks `endsAt > now + 1 s` after its awaits (channel, permission) and returns `null` otherwise; the permission request is one shared in-flight promise (`createPermissionGate`).
- **Android channel id: `timers`** (HIGH importance, default sound, vibration `[0,400,200,400,200,600]`, public lockscreen). Android freezes a channel's importance/sound/vibration after creation: to change them ship a NEW id (e.g. `timers-v2`). The channel is created BEFORE the permission prompt (required for the Android 13 dialog). Permission is requested at the first timer start (once per process); the full permission onboarding (notifications, exact alarms, battery) is M6.
- **Foreground**: `useTimerFeedback()` (mounted in the gym session) ticks every 250 ms, re-syncs when `AppState` becomes `active`, plays 3-2-1 beeps + light haptic, the end alarm + success haptic + `AccessibilityInfo.announceForAccessibility`, and signals cardio segment changes (beep + announced label). While it is mounted the notification handler is silent in the foreground (`setInAppTimerFeedback`); otherwise it shows the banner and sound. A timer that ended more than 3 s ago (in the background) does not ring again on return. Skipping is silent.
- **Sounds**: `assets/sounds/{beep,alarm}.wav`, generated by `scripts/generate-timer-sounds.js`; played with expo-audio `useAudioPlayer` (`seekTo(0)` then `play()`), audio mode `playsInSilentMode: true`, `mixWithOthers`. `expo-keep-awake` (`useKeepAwake`) is active during the session.
- **Exact alarms**: expo-notifications uses `setExactAndAllowWhileIdle` only when `canScheduleExactAlarms()` (Android 12+), otherwise `setAndAllowWhileIdle` (inexact, still delivered in Doze but possibly minutes late). See "Notification scheduler (M6)" for the permission decision.
- The scheduler trims to **64 upcoming notifications on every platform** (not just iOS; Android OEM limits too).

## Notification scheduler (M6)

- **Pure planner** `buildUpcoming(state, from, days = 3)` (`src/domain/notifications`): the window is `from + days × 24 h` (a rolling 72 h, NOT calendar days, so an evening open still plans about three days; it walks `days + 1` logical days and drops what falls after the end). It runs `buildAgenda` for each day and adds the survey and the Sunday review. Stable ids `kind:module:item:yyyy-MM-dd:HH:mm` (local fire time). Quiet hours = circular window from `bed` (exclusive: the "hora de dormir" reminder still goes out) to `wake`; check-ins once a day (wake + 10, bed − 30), skipped today if already done; survey "¿Te moviste hoy?" at `surveyTime` or bed − 90 min (20:00 without a bedtime), skipped today if an activity answer or a finished gym session exists; weekly review Sunday 18:00; reminders of what is done stop for today (`doneAgendaIds`, fed by `loadNotificationPlan` from REAL data: water goal met, a check habit logged today, and the rows acknowledged or skipped in Hoy `todayState`; later days are untouched). Trim to 64: sort by (day, kind priority, time), keep 64, re-sort by time. Template texts are clamped to BRAND §9 (title 30, body 80); built-in texts are i18n keys `notify.*` (a test checks the limits and es/en parity).
- **Scheduler** (`runSync` pure core + `syncNotifications`): resolve texts, `diffSchedule` by id + signature (time, channel, category, text), cancel stale first, then schedule (`scheduleNotificationAsync({identifier})` replaces by id). Only ids starting with `gym|water|habit|checkin|reminder|review|survey:` are managed; timers (uuid) and `snooze:` ids are never touched. No permission -> nothing scheduled; master switch off or onboarding incomplete -> everything of ours cancelled. `requestNotificationSync(reason)` is serialized and coalesced. Every run (foreground triggers AND the background task) goes through ONE promise-chain mutex in `sync.ts` (`runNotificationSync` reports failures, `requestNotificationSync` swallows them and coalesces requests that are still waiting). Triggers: app open / `AppState` active, settings change (Ajustes), onboarding complete, `suggestionAccepted` (a suggestion was accepted), data changes (habit write, check-in saved, gym finished, an answered action) and the background task.
- **Channels** (final list; importance is immutable after creation, so any change ships a NEW id): `gym` (HIGH), `habits`, `checkins`, `reminders`, `review` (the weekly review, own channel so it can be muted alone; DEFAULT) plus `timers` (HIGH, in `src/timers`).
- **Actions with the app closed (verified against the SDK 57 source, `ExpoHandlingDelegate.handleNotificationResponse`)**: all actions are registered with `opensAppToForeground: false`. On Android, when the app is NOT in the foreground and the action is not the default tap, the library runs the TaskManager tasks registered with `Notifications.registerTaskAsync(name)` (docs: "Only on Android, the task also runs in response to a notification action tap when the app is backgrounded or terminated"). So `index.ts` -> `src/notifications/backgroundTasks.ts` defines `pomi-notification-response` at module scope; it runs `bootstrapDatabase()` (the headless run has no app bootstrap) and `applyResponse`. When the JS runtime is alive the listener also fires, so every response is claimed ATOMICALLY once: `settings.claimNotificationResponse(key)` is a single `INSERT ... ON CONFLICT DO UPDATE ... WHERE NOT EXISTS ... RETURNING` over the JSON list in `handledNotificationResponses` (bounded to 40), and `releaseNotificationResponse` gives the claim back when the action throws, so a retry applies it. Writes go to `payload.date` (the day the notification was planned for), not to the day of the tap. The plain tap (default action) is not a task: `useLastNotificationResponse` routes it (check-in -> modal, otherwise Hoy). iOS does not run the task for actions (Pomi v1 is Android only). Category ids use `_`, never `:` or `-` (Expo docs).
- **Categories**: `pomi_habit` (Hecho, Posponer 10 min), `pomi_water` (+1 vaso, Posponer), `pomi_survey` (Fui al gym, Caminé, Hoy no), `pomi_snooze` (Posponer; gym and reminders). Check-ins have no actions ("nunca se insiste"). Snooze schedules the same content at now + 10 min under `snooze:<id>:<at>`.
- **Exact alarms decision**: `SCHEDULE_EXACT_ALARM` (declared in `app.json`) stays OPTIONAL and is justified ONLY by the gym rest timers (end-of-rest alarm); nothing depends on it. Habit, water, check-in and reminder notifications are designed as inexact (a few minutes of slack is fine). Limit: expo-notifications picks `setExactAndAllowWhileIdle` globally whenever `canScheduleExactAlarms()` is true (`ExpoSchedulingDelegate.kt`, no per-notification flag), so once the person grants the special access ALL our notifications become exact; making habits strictly inexact would need native code. **Store release (v4):** Google Play requires a declaration for this permission; describe it as a timer/alarm use (rest timers), and re-check whether `SCHEDULE_EXACT_ALARM` is still allowed for the app category (otherwise drop it: timers fall back to inexact). Chosen over `USE_EXACT_ALARM`: `USE_EXACT_ALARM` is auto-granted but Play restricts it to alarm / timer / calendar apps; `SCHEDULE_EXACT_ALARM` is user-granted ("Alarms & reminders" special access, not pre-granted on fresh installs targeting Android 13+). Android has no JS-readable state for it (expo-notifications exposes none, no new native code), so the screen explains it and opens `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` (`package:` data) through expo-intent-launcher with a `Linking.openSettings()` fallback, and stores a `permissionHints` flag only as a hint. Without it notifications still arrive through the inexact Doze-safe alarm.

- **Background task**: `expo-background-task` (WorkManager, minimum 15 min, we ask for 6 h; the system decides and it stops after a force stop). The library HARDCODES `NetworkType.CONNECTED` in its WorkManager request (`BackgroundTaskScheduler.kt`, SDK 57): it is NOT configurable, so the job never runs offline (an earlier note claimed otherwise). The task runs through the same sync mutex as the foreground triggers and still returns `Failed` on error. It only refills the 3-day window; the window itself is what keeps reminders going if it never runs (3 days). Reboot: expo-notifications restores scheduled alarms on `RECEIVE_BOOT_COMPLETED`. Timezone change: fire times are absolute epoch ms, so they are corrected at the next app open / background run (known, documented).

## Suggestions engine (v2, PLAN §11)

- **Pure** `buildSuggestions(data, today)` (`src/domain/suggestions`): six rules, each `(data, today) => Suggestion | null` returning `{kind, variant, change, textKey, reasonKey, params, evidence}` (i18n KEYS and numbers only). Thresholds live in `limits.ts`. **Priority order** (first wins the weekly slots): deload, sleepEarlier, wakeRegularity, gymDay, stepsGoal, waterEarlier. At most **2 NEW per ISO week** (Monday start, counted over everything created that week, whatever its status); a kind is not offered again while **pending** or for **7 days after an acceptance** (so the change can show its effect); a **rejection blocks per (kind, target)** for 28 days (`targetOfChange`: the weekday moved by `gymDay`, the exercise of a `deload`; the other kinds have one target), so rejecting "move Wednesday" does not hide "move Friday" (the rules skip blocked candidates and offer the next one). **Pending suggestions expire after 7 days** (`PENDING_EXPIRY_DAYS`): `pending(createdSince)` hides them, the next daily run deletes them and `acceptSuggestion` answers `unavailable`.
- **Rules**: _sleepEarlier_ 7-day average (>= 4 mornings) < target − 30 min (strict) -> bedtime 15 min earlier, total drift capped at 60 min. _wakeRegularity_ wake range (circular) > 60 min (strict) over >= 4 mornings -> set `anchors.wake` to the person's usual wake time (median on the circle, rounded to 5 min); silent when the plan already holds that time (owner decision: no no-op question; the median replaces the earlier "plan's wake time" proposal, which was always a no-op for people with a plan). _stepsGoal_ only after the baseline week, >= 5 days with data in each week, `proposeStepsAdjustment` (raise at >= 5/7, lower after two weeks < 3; the previous week is ignored for 14 days after the steps goal changed, by an accepted suggestion OR a manual edit: `goalsChangedOn`). _waterEarlier_ < 60% (integer compare, 3 of 5 is NOT short) of the day's glasses at 18:00 on >= 5 of the last 7 finished days that have at least one write (days without any log are skipped, not counted as 0%; the reason says "N de los M días que registraste") -> reminders 30 min earlier, cap 120 min. _gymDay_ a planned weekday missed 3 of the last 4 weeks (needs four full weeks with the CURRENT plan: since the later of `startedOn` and `gymDaysChangedOn`; attendance = finished session with sets OR a "Fui al gym" answer) -> moved to a free weekday the person already trains on, else the next free one. _deload_ is **reactive only** and blocked for 14 days after a deload week ended (`deloadWeek.endsOn`, `DELOAD_BLOCK_DAYS`) (`isStalled`, exported from `todayTarget`, same `stallSessions`/`deloadPct` as the Gym tab; docs/evidence/training.md section 5: no scheduled deloads).
- **Data model additions**: table `habit_events` (migration 0003): every `habitLogs.set/increment/decrement` appends `{habitId, date, at, value after}` (the daily total cannot answer "water by 18:00") in the SAME transaction as the log write (these methods open a top-level `withTransaction`: never call them inside another callback) and prunes events older than 30 days. `settings.set('gymDays' | 'goals')` also stamps `gymDaysChangedOn` / `goalsChangedOn` (day keys) when the value really changed, whoever changed it; the engine reads the stamps instead of guessing. Evidence carries `unit: 'days' | 'sessions'` ("Basado en N sesiones" for a deload; rows stored without `unit` count days). Events exist only from this version on, so the water rule stays silent for the first week. It is part of the backup (`habitEvents`, optional with default `[]` so older v1 files still restore). Settings: `planShifts` (`bedMin` >= -60, `waterMin` >= -120, minutes EARLIER), `deloadWeek` `{startsOn, endsOn, pct}`, `suggestionsLastRun`.
- **How accepted changes take effect**: the planned bedtime is `wake − sleepTargetH + bedMin` (`resolveAnchors(anchors, shifts)`, also the morning check-in prefill; the target hours themselves do not change, so the rule cannot chase itself); water reminders are shifted earlier in `buildAgenda` (never before wake + 10 min); the steps goal becomes `goals.stepsGoal`; a gym day moves inside its own morning/evening entry of `gymDays`; a deload week lowers every working weight by `pct` for 7 days from the acceptance (`applyDeload`, reason `gym.target.deloadWeek`; sets are not reduced).
- **Run**: `runDailySuggestions(db, repos, now)` runs at most once per logical day (`suggestionsLastRun`, read AGAIN inside one serialized `withTransaction` together with load, build and insert, so the foreground reload and the background task cannot store duplicates), after the onboarding, from the Hoy reload and from the background sync task, and stores `pending` rows (`kind`, `reason` = i18n key, `payload` = variant + change + params + evidence). Hoy shows the OLDEST pending one as `SuggestionCard` (mascot `curioso` sm, the text, "Por qué: ...", "Basado en N días", Aceptar / Ahora no). **Aceptar**: `acceptSuggestion` re-validates against the CURRENT plan (`isChangeStale`: the `from` value moved, the weekday is gone, the wake time is already set, a deload is running, the steps goal changed since; stale or expired -> `unavailable`), applies the patch and marks it accepted in ONE `withTransaction`, then `requestNotificationSync('suggestionAccepted')` and a toast (announced by TalkBack). **Ahora no**: fade (120 ms with reduce motion), then `rejectSuggestion`.
- Tests: every rule at its boundaries, the weekly maximum, the 4-week block, no duplicates, the 60-day synthetic generator, applying each change against the real migrations (including rollback), the water value at 18:00 from events, texts with all placeholders in es and en, `TodayScreen` with a suggestion.

## Progreso tab (v2, PLAN §13, HANDOFF §2 and §8)

- **Strength metric = estimated 1RM (Epley) of the best set of each day**, per exercise (step id): `e1RM = weight x (1 + reps / 30)`, one rep = the weight itself. Chosen over "top weight" because a double-progression program (more reps, then more kg) moves e1RM on both axes. It is an ESTIMATE and the screen says so ("kg estimados", "fórmula de Epley, no un máximo real"). Sets above 12 reps (Epley drifts) and sets without weight (bodyweight) are left out; several sessions in one day merge into one point. Window: 26 weeks of finished sessions with sets (`STRENGTH_LOOKBACK_DAYS`).
- **Consistency per week** (`weeklyBuckets`): ISO weeks (Monday), the last 8, ending with the current one (energy color). Per week: finished gym sessions with sets against the PLANNED weekdays (`plannedPerWeek(gymDays)`; the planned amount is an outline behind the bar, so a shorter bar is "less this week", never a failure) and the number of days with any habit value logged (0-7). Weeks before `startedOn` are not shown. Dates are logical day keys, so a 00:30 session belongs to the day that was ending.
- **Measurements**: the metrics come from the ACTIVE `metricas` module (`peso` weekly, `cintura`/`cadera`/`gluteo` monthly); `metric_entries` is one value per day (`metrics.upsert`). `MeasurementCard` shows the latest value, a chart from one point on, a gentle "Toca registrar esta semana/este mes" (`isEntryDue`, never a miss) and the entry form (`parseMetricInput`: comma or dot, one decimal, plausible range per unit, readable errors).
- **A11y summaries**: every chart is one accessible `image` whose label is a sentence, e.g. "Hip thrust: de 40 a 50 kg estimados en 8 semanas." (`progress.strength.summary*`); bars list each week. States: skeleton only after 300 ms (`useDelayedFlag`, `Skeleton`), `EmptyState compact` per section, tablets (`layout.twoColumnMin` 600) get two columns and `Screen wide` (`layout.wideContentWidth` 1120). The photos grid shows the newest 12 photos (see "Monthly review with photos"); the findings section is a placeholder until v3, no fake data.
- Tests: pure series/buckets/metrics (`src/domain/progress`), `progressView`, `loadProgressData` against the real migrations, chart components and `useDelayedFlag`, `ProgressScreen` states (empty, summaries, entry form, retry).

## Backup and program import (M7)

- **Backup file** (`pomi-backup`, `schemaVersion` 1): `{format, schemaVersion, appVersion, exportedAt, includesPhotos, data}` where `data` has one array per table (rows use the Drizzle camelCase names, `settings` rows keep their JSON text). Export is a plain SELECT per table in primary-key order; restore (`restoreBackup`) deletes every table (children first) and inserts the rows in chunks inside ONE `withTransaction`, so any failure (CHECK, FK, duplicate key) rolls back and leaves the current data untouched. Photo ROWS are exported only when `includesPhotos` is true (default false); a restore ALWAYS clears the photo rows and re-inserts them only from a backup that includes them (the preview says so: "quitará las fotos que tienes ahora"). When the schema changes, bump `BACKUP_SCHEMA_VERSION` and add `BACKUP_MIGRATIONS[previousVersion]` in `parse.ts` (`migrateBackupJson` walks the chain and stamps each version; a missing step means `olderVersion`; the table is empty today).
- **Restore isolation (maintenance gate, `src/db/maintenance.ts`)**: `restoreBackupExclusive` runs the restore through `runMaintenance(db, work)`. The busy flag (`useMaintenanceStore`, rendered by `MaintenanceOverlay`, a full-screen Modal mounted in `app/_layout.tsx` that swallows touches and the back button) turns on immediately; the GATE goes up from INSIDE the top-level transaction slot (after every transaction already running has finished: raising it earlier would deadlock a transaction that awaits a gated repository call) and comes down after commit/rollback. While it is up, every method of the `getRepositories()` singleton (wrapped by `gateRepositories`), `runNotificationSync` / `requestNotificationSync` (inside the sync mutex), `runDailySuggestions` and therefore the background tasks wait on `waitForMaintenance()`. Plain `createRepositories(db)` (tests, the restore itself) is NOT gated. Work inside `runMaintenance` must use the `tx` / raw `Db`, never `getRepositories()` (it would wait for itself). Hydrating stores and `requestNotificationSync('dataChanged')` run AFTER the restore returns.
- **Picked-file caps** (`limits.ts`, checked on the picker asset and on the cached copy BEFORE `File.text()`): 50 MB for backups, 1 MB for programs; `FileTooLargeError` -> readable message with the cap. **Export file hygiene**: stale `pomi-backup-*.json` in the cache are removed before each export; the exported file is deleted right away on failure and 60 s after a successful share (Android's chooser resolves as soon as a target is picked while that app may still be reading the content URI, e.g. a cloud upload), the picked cache copy is deleted after reading.
- **Restored JSON columns** (`payloads.ts`): `suggestions.payload` must match its kind (known kind, `suggestionPayloadSchema`, change type for that kind), `insights.evidence` must be an object or list, `reminders.schedule` a template `Schedule`, `checkins.answers` a record of text/number (the Drizzle column type is `Record<string, string | number>`).
- **Validation** (`parseBackupText`): JSON syntax (with line), `format`, version (older/newer have their own message), zod for every row (paths like `data.stepsDaily[0].steps` through the importer's `issueToErrors`), every setting key must be known and its value valid, every template goes through `importTemplate`, set logs must point to an existing session. Messages are Spanish/English via `describeBackupError` (reuses `importErrors.*`).
- **Flow** (Ajustes > Respaldo): export writes the JSON to the cache dir and opens the share sheet; import picks a file (`type: '*/*'` because Android labels `.json` as octet-stream; `copyToCacheDirectory` must stay true so `File.text()` can read it), shows counts and asks for confirmation ("Reemplazar todo"). After a restore: `hydrateStores` (theme, language, onboarding status from the DB) and `requestNotificationSync('dataChanged')`.
- **Gym program import** (Ajustes > Importar programa de gym, `src/templates/programImport.ts`): same template importer, preview (modules with programs, routine counts, "exists"), mode `replace` / `add`; applied in one transaction through `templates.saveModulesIn` / `listModulesIn(tx)` / `setActiveIn(tx)` (only the `...In` forms inside the callback). The preview lists the impact (`computeImportImpact`, pure; it follows the chosen mode): exercises WITH logged sets whose step id is missing from the replacing module (their history stops showing, because the history key is the step id; `workouts.loggedStepIds()`) and the other active modules with a program that will be switched off. The app trains ONE program (first active module with one), so the imported modules are activated and other modules with programs are switched off. A file without programs is rejected (`noProgram`).
- Tests: `src/backup/backup.test.ts` (round trip of every table, photos opt-in and cleared on restore, corrupt / old / new / foreign files, per-kind payloads, migration chain, rollback), `src/backup/limits.test.ts`, `src/db/maintenance.test.ts` (gate, no deadlock with a running transaction) and `src/templates/programImport.test.ts`. The screens and the file picker/share sheet are NOT covered by Jest.

## Gym session (M4)

- **Gym tab**: `useGymTab()` loads the first program of the first active module (`pickProgram`), today's routine (`todaysRoutineId` over the last 40 sessions) and any resumable unfinished session of today (with sets). "Empezar"/"Continuar" and every routine card open `app/gym/session.tsx?routineId=...`.
- **Session**: the DB row is created LAZILY on the first ✓ (opening a routine and leaving leaves no trace). Reopening a routine resumes today's unfinished session of that routine (`unfinishedSessionOn(date, routineId)`). Warm-up/cardio checks (non-`sets` steps) are NOT persisted (in memory only), so they reset on resume; sets are.
- **History for targets**: `recentSessionsForStep(stepId, stallSessions + 2, currentSessionId)` (finished sessions only, most recent first) feeds `todayTarget`; stored sets are converted with gaps filled so skipped sets keep their index.
- **✓ semantics** (`setActions.ts`): medium haptic, rest timer starts BEFORE the write (rolled back if the write fails), empty inputs use the "anterior" value, then today's target (`resolveSetValues`); RIR chosen before ✓ is logged with it, after ✓ it edits the log. ✓ again unlogs and cancels that set's rest. Bodyweight sets never log a weight; `holdSec` sets get a hold-timer button.
- **UI tokens added**: `ring.size` 160 / `ring.stroke` 12 (TimerRing). `TimerSheet` and `Toast` are in `src/ui`.
- **Session writes**: ✓ / un-✓ / RIR on the same set run through `createKeyedQueue` (`asyncControl.ts`, key `stepId:setIndex`), so a quick ✓ then un-✓ cannot leave a ghost set; session creation is `memoizeUntilFailure` (a failed creation is retried). A failed ✓ or finish shows an error `Toast` and the session stays open. Typed numbers are validated (`parseKgInput` `^\d{1,4}([.,]\d)?$` rounded to 0.1, `parseRepsInput` `^\d{1,3}$`, at least 1): invalid text shows an inline error and is never replaced by the previous value; empty uses the previous value. `formatKg(value, language)` shows "42,5" in Spanish (target messages go through `localizeTargetParams`).
- **Render cost**: `TimerSheet` owns the 250 ms clock (`useNow`); the session screen subscribes to primitive timer selectors only; `ExerciseCard` / `SetRow` are `React.memo` with stable handlers (they receive `step` / `index` as arguments) and `groupLogsByStep` keeps the array of an unchanged step.
- Testing: timer model/store with fake effects; `useTimerFeedback` with mocked expo-audio/haptics (`jest.mock` factories must only touch `mock*` variables lazily); SetRow/ExerciseCard with RNTL (`setLanguage('es')` in `beforeEach`, the test env defaults to English).

## Database conventions (M1)

- Drizzle + expo-sqlite (`openDatabaseSync('pomi.db')`, `PRAGMA foreign_keys = ON`). Day keys are `yyyy-MM-dd` text; timestamps are integer epoch ms; JSON columns use `text({ mode: 'json' })`.
- Schema changes: edit `src/db/schema.ts`, run `npm run db:generate`, commit `drizzle/` + `src/db/migrations.generated.ts`. Migrations are bundled as strings by `scripts/build-migrations.js`, so there is NO `babel.config.js`, no `babel-plugin-inline-import` and no Metro `.sql` rule. Do not use the `drizzle/migrations.js` that drizzle-kit emits (the script deletes it).
- Migrations run under the splash: `app/_layout.tsx` waits for `useDatabaseReady()` before rendering. The DB is opened LAZILY inside a module-level bootstrap promise (`bootstrapDatabase()`: open, `migrate`, seed templates, hydrate theme/language), so an open/migrate failure shows the localized error screen instead of crashing at import, and StrictMode's double effect shares one run (a failure is not cached, so a remount retries). Errors are logged in `__DEV__`.
- **Tests run in `TZ=America/New_York`** (`jest.global-setup.js` sets it in the parent process, so every worker inherits it): the suite no longer depends on the machine's zone and `src/domain/timeDst.test.ts` exercises a real 23 h and 25 h day. **Day rollover (04:00 local):** a "day" for logs runs 04:00 -> 03:59 (PLAN §10), so a night check-in at 00:30 belongs to the day that is ending. The ONLY function that turns a moment into a `yyyy-MM-dd` log key is the pure `dayKeyFor(date, rolloverHour = DAY_ROLLOVER_HOUR)` in `src/domain/time.ts` (with `dayStartFor` = the logical day's local midnight and `minutesIntoDay` = WALL-CLOCK minutes since it (calendar days apart x 1440 + local time of day), `>= 1440` between 00:00 and 04:00, matching the agenda convention; deliberately NOT elapsed milliseconds, because every agenda minute is turned back into a Date with `new Date(y, m, d, 0, minutes)`, so on a DST day elapsed time would be an hour off from the agenda; the DST test checks the round trip). Use it for habits, water, check-ins, activity, steps (manual and Health Connect), Hoy (`loadTodayData`: agenda weekday, timeline minute, snooze offsets), the gym session date/weekday, notification responses, the scheduler (`buildUpcoming` day 0 is the logical day, so the "done today" flags apply to it; notification `data.date` is the logical day) and onboarding `startedOn`. Never call `format(date, 'yyyy-MM-dd')` for a log key; formatting a CALENDAR date (a notification id fire time, Health Connect slice days) is fine. Hoy reloads when the logical day changes while the app is open. `CheckinScreen` captures the key ONCE at open and uses it for prefill and save.
- Repositories (`src/db/repositories/*`) are factories over an injectable `Db` (`BaseSQLiteDatabase<'sync' | 'async'>`). Always `await` queries; no driver-specific APIs. For atomic work use `withTransaction(db, async () => ...)` (`src/db/transaction.ts`): it issues BEGIN/COMMIT/ROLLBACK through `db.run` (Drizzle's `db.transaction` is sync on expo-sqlite and async on the test proxy). Top-level calls on one `Db` are SERIALIZED by a promise-chain mutex; nesting is explicit: the callback receives a `tx` handle, and `withTransaction(tx, ...)` uses a savepoint (a plain `db` always starts a new top-level transaction, so never do that inside a callback: it would wait for itself). A failed rollback never masks the original error. The connection is shared, so unrelated queries awaited inside the callback join the transaction; keep callbacks short. They hold no domain logic. **Limits:** there is no timeout (a callback that never settles blocks every later top-level transaction on that `Db`), so never await network, UI or timers inside; the lock is per `Db` object, not per process. Repository methods that open their own top-level transaction come in pairs: `foodNotes.save` / `saveIn(tx, ...)` and `templates.saveModules` / `saveModulesIn(tx, ...)`; inside a callback use the `...In` form, which REQUIRES a `Tx` (the type system stops the deadlock; a top-level re-entry cannot be detected at runtime on React Native, there is no AsyncLocalStorage). App code uses the `repositories` singleton from `src/db`; never import `src/db/client` from domain code or tests.
- Settings are a typed k/v (`settingsSchemas` in `repositories/settings.ts`, zod-validated on read): `anchors`, `gymDays`, `themeMode`, `language`, `activeModules`, `checkinPrefs`, `templatesSeeded`, `onboardingComplete`, `userName`, `stepsEstimate`, `goals`, `startedOn`, plus `notificationPrefs`, `todayState`, `handledNotificationResponses`, `permissionHints`, `planShifts`, `deloadWeek`, `suggestionsLastRun`, `gymDaysChangedOn`, `goalsChangedOn`. `templates.active` = module installed/enabled; `activeModules` = user feature toggles from onboarding.
- Repository tests run on Node's built-in `node:sqlite` through Drizzle's sqlite-proxy (`await createTestDb()` in `src/db/testing/createTestDb.ts`). It runs the bundled migrations through Drizzle's REAL dialect migrator (journal, `__drizzle_migrations` table, transaction), the same code path as the app. No better-sqlite3. Requires Node >= 22.13 (`.nvmrc` = 22).
- Enum columns (`source`, `kind`, `status`) and `set_logs.rir` (0-3) have CHECK constraints; `metric_entries` is unique on `(metric_id, date)` and writers must upsert (`repositories.metrics.upsert`). Migration `0001` recreates tables (SQLite cannot add CHECKs in place); it was hand-edited after generation to dedupe `metric_entries` (keeps the max id), null out `rir` outside 0..3, normalize unknown enum values and drop rows with unknown `kind` before the INSERT...SELECT (`src/db/migrations.test.ts` seeds an old-schema DB with `createTestDb({ migrationLimit: 1 })`). The `PRAGMA foreign_keys` lines were removed: the migrator runs inside a transaction, where SQLite ignores that pragma.
- `workouts.lastSessionForStep` / `recentSessionsForStep` count ANY session with at least one logged set for the step (finished or not; the session in progress is excluded by id), ordered by `startedAt desc, id desc`. `workouts.finishStaleSessions(today)` (called when the Gym tab / a session loads) closes sessions left open on earlier days at their last set's `doneAt`. `workouts.updateRir` changes only the RIR (keeps `doneAt`).
- Importer rules added after M1 review: a `when` condition needs `days` (min 1) or `flag`, `flagValue` needs `flag`; duplicate ids are errors for step ids WITHIN a routine, habit ids within a module, and module ids within a bundle. The same step id across routines of a program is deliberate (shared history, e.g. common warm-up), so it is allowed. `Template` derives from the single `KIND_SCHEMAS` map in `src/templates/schema.ts`.

## Domain conventions (M2)

- `src/domain/**` is pure TypeScript: no React, React Native, Expo, Drizzle or `src/db` imports (enforced by `src/domain/domain.test.ts`). `date-fns` and type-only imports from `src/templates/schema` are fine. Input in, value out; no clock access (callers pass the date).
- Time of day is `HH:mm` strings or minutes of the day (`time.ts`). Everything crossing midnight wraps; agenda minutes `>= 1440` mean "after midnight, end of today's timeline" (a bed time of 00:30 is 1470). A derived bed is pushed past midnight only when its clock is before wake AND before 06:00 (late wakers, e.g. wake 11:00 + 8 h -> 03:00; a shifted day like wake 15:00 -> bed 07:00 stays 07:00). Relative offsets wrap into 0..1439; only `bed`-relative values may stay `>= 1440`. A repeating schedule with `until` before its start crosses midnight. Several `gymDays` entries on one weekday yield ONE gym item with all occurrences. Agenda ids include the module id (`habit:<module>:<habit>`). `evaluateWhen([])` holds (no constraint; the schema rejects empty lists/conditions).
- Domain functions return i18n KEYS + params (`TargetMessage`), never text. Keys live in `src/i18n` (`gym.target.*`, `agenda.*`); tests assert every emitted key exists.
- **Water:** `waterGoal({weightKg, gymHours, glassMl})` -> `{rawMl, glasses, ml}`; rounds up (float noise guarded). **Steps:** baseline = mean of the last 7 days (needs >= 3, else the onboarding answer); `initialStepsGoal` = baseline + 1000 to nearest 500, capped; `proposeStepsAdjustment` is a pure PROPOSAL (raise at >= 5/7; lower after 2 consecutive weeks < 3 days, floor = baseline; the caller passes `daysMetPreviousWeek: undefined` after a goal change).
- **Sleep:** bedtime = wake − target; wake regularity = circular RANGE (max − min) of wake times over the last 7 morning check-ins (matches the ">60 min" rule); cycles calculator = wake − n×90 − 15 (n = 4..6).
- **reps parser:** returns `{kind:'reps', min, max, perSide}` or `{kind:'time', minSec, maxSec, perSide}` (seconds, minutes are converted) or `null`; first range wins in compound text; a leading `3x` set count is ignored (`3x8–10` -> 8..10).
- **Rotation:** routine with sets logged today > next after the last COMPLETED session (wraps) > first.
- **todayTarget:** history is per step id, most recent FIRST. Working weight = heaviest set. Case 1 needs every planned WORKING set (sets at the heaviest weight; lighter warm-up/drop sets are ignored) at the top with RIR >= 1/unknown; no `incrementKg` -> best last set + 1 rep, beyond the range (11 -> 12). Case 2 adds +1 rep (capped at the top, floored at the min) to EVERY set below the top, indexed over the unfiltered last session so skipped sets do not shift positions; the reason reports the smallest raised target. A weight drop of about `deloadPct` (+-5 points) resets the stall window. Stall = each of the last `stallSessions` sessions failed to beat its predecessor (needs `stallSessions + 1` sessions); deload weight rounds to 0.5 kg. RIR >= 3 on every set (all recorded) for 2 sessions -> "go heavier" suggestion.
- **buildAgenda(date, state):** gym comes from settings `gymDays`/anchors (never `program.schedules`); `bed` is derived; habits are filtered by `onlyIf` (`profile.*`), steps by `When`; a habit whose schedules do not apply today is dropped; all-day items (steps, unscheduled habits) sort last. Water goal uses 1 h of gym on gym days.
- `src/domain/testing/syntheticData.ts`: seeded 60-day generator (gym -> +35 min sleep, later weekends, afternoon water dip) for suggestion/insight/chart tests.
